## مفهوم

**Doorway abuse** یعنی سایت یا صفحه‌هایی بسازی تا برای تعداد زیادی کوئری شبیه رتبه بگیرند و کاربر را از یک واسطهٔ کم‌فایده به مقصد مشترک هل بدهند. قالب شهر × خدمت، چند دامنه برای واریانت منطقه‌ای و صفحه‌هایی که فقط یک کلمه فرق دارند ولی همه به یک checkout یا فرم می‌روند، الگوهای رایج‌اند.

هر صفحهٔ لوکیشن یا سرویس doorway نیست. صفحهٔ مشروع باید نشان بدهد واقعاً در آن بازار سرویس می‌دهی و مدرک یکتای قابل بررسی داشته باشد: تیم یا شعبه، محدودهٔ پوشش، مجوز و محدودیت محلی، قیمت یا زمان تحویل، پروژهٔ انجام‌شده، نظر مشتری، موجودی و راه تکمیل همان کار.

خط مرزی تعداد کلمه نیست. ببین URL کار مستقل و شاهد معتبر دارد یا فقط واسطه‌ای برای گرفتن جای بیشتر در نتایج است.

## چرا مهم است

ژنراتور doorway یک‌باره crawl waste، صفحهٔ ضعیف، نویز analytics و بدهی نگه‌داری می‌سازد. موقع حذف هم اگر همه را کورکورانه به یک money page ریدایرکت کنی، مشکل دوم درست می‌شود.

<CorrectExample title="درست">
`/locations/shiraz/heat-pump-installation` چون شرکت واقعاً شیراز را پوشش می‌دهد منتشر شده. تیم مسئول، محدودهٔ سرویس، روند مجوز محلی، مدل‌های موجود، بازهٔ نوبت، دو نصب مستند و تماس مرتبط بازار را دارد. کاربر همان‌جا می‌تواند درخواست سرویس بدهد.

شهری که خارج از پوشش است صفحه ندارد. راهنمای عمومی نصب هم یک‌بار در بخش منابع منتشر شده.
</CorrectExample>

<IncorrectExample title="غلط" why="صفحه‌ها واریانت کوئری را هدف گرفته‌اند، اما سرویس، شاهد یا مقصد جدا ندارند و همگی واسطهٔ نازک یک فرم مشترک‌اند.">
CMS از CSV تعداد ۶۰۰ صفحهٔ `/plumber/{city}` می‌سازد. فقط نام شهر عوض می‌شود. شعبه، تکنسین، ظرفیت، پروژه و تماس محلی وجود ندارد. همهٔ CTAها به یک فرم فروش lead کشوری می‌روند.
</IncorrectExample>

## پیاده‌سازی وردپرس

**Yoast SEO**

1. صفحهٔ لوکیشن واقعی را indexable و در sitemap نگه دار؛ taxonomy خالی و خروجی ژنراتور را منتشر نکن.
2. امتیاز سبز محتوا ثابت نمی‌کند لوکیشن واقعی یا صفحه یکتاست.

**Rank Math**

1. قبل از import داده، متغیرهای Titles & Meta و CPTهای فعال در sitemap را بازبینی کن.
2. doorway حذف‌شده را فقط وقتی 301 کن که مقصد نزدیک واقعاً همان intent را جواب دهد؛ وگرنه `410` یا `404`.

**AIOSEO**

1. فیلدهای Local SEO باید دفتر/محدودهٔ واقعی و شاهد یکدست کسب‌وکار را نشان دهند.
2. یک رکورد schema را برای لوکیشن خیالی clone نکن.

**SEOPress:** وقتی Local Business یا redirection آن مالک داده است تفاوت اجرایی دارد؛ شرط شاهد و مرتبط بودن مقصد همان می‌ماند.

**جا خالی واقعی:** افزونه metadata، sitemap و redirect را کنترل می‌کند، ولی نمی‌فهمد تیم واقعاً شهری را پوشش می‌دهد یا case study ساختگی است. CRM/عملیات و تأیید تحریریه باید gate انتشار باشند.

## پیاده‌سازی Next.js

Route را فقط از رکورد سرویس تأییدشده و دارای شاهد بساز:

```tsx
import { notFound } from "next/navigation";

import { getApprovedServices, getService } from "@/lib/services";

export async function generateStaticParams() {
  const services = await getApprovedServices();
  return services.map(({ city, service }) => ({ city, service }));
}

export default async function ServicePage({
  params,
}: {
  params: Promise<{ city: string; service: string }>;
}) {
  const { city, service } = await params;
  const record = await getService(city, service);

  if (!record?.published) notFound();
  return <main><h1>{record.title}</h1><p>{record.localEvidence}</p></main>;
}
```

در App Router فعلی، `params` پویاست و باید await شود. `generateStaticParams` جای `getStaticPaths` در Pages Router را گرفته و باید از رکورد واقعی بخواند، نه از لیست عمومی شهرها. فقط وقتی ترکیب تولیدنشده باید 404 شود `dynamicParams = false` را بررسی کن.

یادداشت Pages Router: رکورد را در `getStaticPaths`/`getStaticProps` اعتبارسنجی کن و برای ترکیب پشتیبانی‌نشده `notFound: true` بده. مسیر `[city]/[service]` فقط وقتی مشروع است که دادهٔ زیرش مشروع باشد.

## اشتباه‌های رایج و افسانه‌های منسوخ

- **DEPRECATED:** «سیصد کلمهٔ یکتا هر صفحهٔ شهر را امن می‌کند.»
- **DEPRECATED:** «Canonical کردن doorway به hub سوءاستفاده را خنثی می‌کند.»
- **DEPRECATED:** «Programmatic SEO چون structured data دارد خودکار compliant است.»
- چرخاندن همان case study بین چند بازار.
- ساخت صفحهٔ «نزدیک من» بدون مقصد یا خدمت محلی.
- 301 همهٔ شهرهای حذف‌شده به homepage یا یک فرم کشوری.

## نکته‌های سطح بالا / پروداکشن

انتشار را قرارداد عملیاتی کن: هر رکورد active service، مالک شاهد، تاریخ آخرین تأیید و رفتار خروج داشته باشد. وقتی پوشش تمام شد خودکار از انتشار بیرون بیاید، ولی مقصد redirect را انسانی بررسی کن.

Similarity detection فقط سیگنال triage است، نه حکم. بعضی اطلاعات قانونی باید تکرار شوند و شاهد یکتا ممکن است کوتاه باشد. نمونهٔ مدرک first-party را با تیم عملیات تطبیق بده.

برای cleanup، اول ژنراتور را ببند، URLها را بر اساس ارزش کاربری دسته‌بندی کن، duplicate واقعی را ادغام کن، صفحهٔ بدون پشتیبانی را بردار و لینک داخلی و sitemap را اصلاح کن. شعبه، review یا پروژهٔ جعلی نساز و برای ریکاوری زمان قول نده.

## چطور مطمئن شوی

| بررسی | قبول | رد |
| --- | --- | --- |
| شاهد سرویس | تیم، موجودی، پروژه یا شعبهٔ فعال | فقط توکن شهر |
| نتیجه برای کاربر | کار در همان صفحه تمام می‌شود | قیف به واسطهٔ مشترک |
| crawl شباهت | واقعیت مشترک + مدرک متمایز | بدنهٔ تقریباً یکسان در مقیاس |
| منبع route | رکورد عملیاتی تأییدشده | ضرب دکارتی شهر و خدمت |
| بازبینی redirect | ادغام مرتبط یک‌به‌یک | همه به homepage |

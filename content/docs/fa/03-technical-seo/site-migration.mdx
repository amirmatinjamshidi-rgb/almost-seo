## مفهوم

مهاجرت هر تغییری است که **URL قدیم دیگر آن سند نباشد**: دامنه، HTTPS، CMS، پوشه، اسلش انتهایی، پیشوند زبان، ادغام دو سایت.

گوگل نیاز دارد: **نقشهٔ 1:1 (یا many:1)** به بهترین معادل، **ریدایرکت دائمی**، **لینک داخلی** به‌روز، **canonical**، **sitemap**، و **GSC** روی property جدید. هاست قدیم تا وقتی لینک می‌گیرد به 301 جواب بدهد (سال‌ها، نه آخر هفته).

نوع: لیفت همان-URL (HTTP به HTTPS)، تغییر مسیر، تغییر دامنه، ادغام، شکاف (سایت کشور). سختی کیفیت نقشه است، نه برند CMS.

درخت جدید را وقتی درخت قدیم هنوز همان title را `200` می‌دهد لانچ نکن (duplicate). روز اول درخت قدیم را «چون sitemap جدید است» 404 نکن.

## چرا مهم است

مهاجرت پرریسک‌ترین پروژهٔ سئوی تکنیکال است. نمودار ترافیک که ۸۰٪ می‌افتد معمولاً 301 جاافتاده، robots روی هاست جدید، یا canonical هنوز به دامنهٔ قدیم است.

<CorrectExample title="درست">
اسپردشیت (در git): `old_url,new_url,status`. هر URL پول‌ساز قدیم با `curl` یک 301/308 می‌شود. URL جدید `200`، self-canonical، در sitemap. Change of Address در GSC **فقط** برای جابه‌جایی دامنه، بعد از verify هر دو property. sitemap قدیم می‌تواند URL قدیمی که 301 می‌شود را لیست کند (یا sitemap جدید را روی property جدید submit کنی). لینک داخلی سایت جدید به URL جدید می‌زند.
</CorrectExample>

سایت جدید می‌آید؛ URL قدیم 404؛ canonical قاطی HTTP/HTTPS؛ `Disallow: /` جامانده روی robots.txt جدید؛ GSC هیچ‌وقت property جدید نگرفت؛ 302 «تا مطمئن شویم.»

## پیاده‌سازی وردپرس

**Yoast SEO**

1. بعد از تغییر URL، sitemap را دوباره بساز. canonical باید `home` جدید را استفاده کند.
2. ایمپورت ریدایرکت Premium از CSV نقشه. بکاپ export.

**Rank Math**

1. Redirections ← import. 301 بگذار، نه 302.
2. Instant Indexing روی URL جدید بعد از باز بودن robots — هنوز جایگزین 301 از هاست قدیم نیست.

**AIOSEO**

1. ایمپورت addon Redirects. همان انضباط CSV.
2. verification ابزار وبمستر را روی هاست **جدید** به‌روز کن.

**جا خالی واقعی:** پلاگین تگ را جابه‌جا می‌کند؛ DNS یا TLS را نه. ایمپورت SEOPress شبیه است. برای جابه‌جایی دامنه، 301 سرور/CDN از هاست **قدیم** مهم‌تر از پلاگین WP روی هاست جدید است.

## پیاده‌سازی کد

```ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  async redirects() {
    return [
      {
        source: "/old-guides/:slug",
        destination: "/guides/:slug",
        permanent: true,
      },
    ];
  },
};

export default nextConfig;
```

App Router: `metadataBase` = origin جدید. `sitemap.ts` فقط canonical **جدید** بدهد. برای هاست میراث نقشهٔ لبه نگه دار.

Pages Router: همان `redirects()`. به `router.replace` کلاینت تکیه نکن.

ران‌بوک cutover (ترتیب مهم است): فریز محتوا ← دیپلوی جدید ← روشن کردن 301 روی قدیم ← submit sitemap ← نگاه به لاگ/GSC ← درست کردن جاافتاده ← فقط بعد 200های باقی مسیر قدیم را بکش.

## اشتباه‌های رایج و افسانه‌های منسوخ

- **DEPRECATED:** «اگر ping کنی گوگل در ۴۸ ساعت همه‌چیز را دوباره crawl می‌کند.»
- **DEPRECATED:** Change of Address به‌عنوان تعمیر جابه‌جایی فقط-مسیر (برای تغییر دامنه است).
- فقط rel=canonical به‌جای 301 وقتی URL قدیم باید بمیرد.
- لانچ با `noindex` استیجینگ هنوز روشن.
- ریدایرکت همهٔ URL قدیم به `/` برای «نگه داشتن PageRank.»

## نکته‌های سطح بالا / پروداکشن

URL را طبقه کن: نگه دار، ریدایرکت، 410. محتوایی که می‌میرد نباید به hub نامرتبط 301 شود (شبیه soft-404).

اندازه: درصد ضربهٔ Googlebot روی هاست قدیم که 301 است، تعداد URL ایندکس‌شده قدیم در مقابل جدید، landingهای برتر قبل/بعد (اول کوئری برند، بعد head term — ساعت بازیابی فرق دارد).

اگر CMS **و** IA را یک‌جا عوض کنی، نمی‌فهمی کدام شکست. وقتی کسب‌وکار اجازه داد بشکن.

جفت hreflang باید با هم جابه‌جا شوند وگرنه خوشهٔ شکسته می‌فرستی.

## چطور مطمئن شوی

| ابزار | قبول | رد |
| --- | --- | --- |
| نمونهٔ ۱۰۰ URL پول‌ساز قدیم | 301 به 200 درست | 404، خانه، حلقه |
| هر دو property در GSC | sitemap جدید fetch شده؛ 404ها توضیح دارند | سایت جدید «excluded by robots» |
| لاگ | Googlebot 301 را دنبال می‌کند | هنوز 200 روی duplicate قدیم |
| crawl داخلی سایت جدید | هاست قدیم جا نمانده | لینک مطلق به دامنهٔ مرده |
